{% load i18n %} {% comment %} Add-element menu. At top level it offers every type; inside a container (nested=True) it carries the scope (data-parent/data-tab) so the add posts land the child in the right slot, and it hides the non-nestable groups. `depth` is the depth of the menu's PARENT -- 0 for the top-level menu, N for a menu rendered inside a row at depth N -- so a child added here lands at depth `depth|add:1`. `max_nest_depth` comes from the view as builder.MAX_NEST_DEPTH (a module attribute, so a monkeypatched cap really reaches this template). The CONTAINER cards (Tabs, Columns, Spoiler, Callout) are guarded by `depth < max_nest_depth|add:-1`, which mirrors builder clause 4 exactly: a container child is accepted while its parent sits at depth 1 or 2 (so the child lands at depth 2 or 3) and rejected from depth 3 down. Leaves stay offered at depth 3 because they land at depth 4, which clause 3 accepts. Hiding the cards is COURTESY only -- the server still enforces NESTABLE_TYPE_KEYS and the depth clauses on every add/save, so a hand-crafted POST for a blocked type or an over-deep parent is rejected regardless. A row already at the cap gets no menu at all; that guard lives on the include in _element_row.html, not here. {% endcomment %}
